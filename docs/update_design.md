# 更新方式设计

2026-10-14 用户定：发给朋友试玩之前，先做好主程序更新和插件更新。第一份给朋友的包里必须已经带着更新功能，否则这份包以后没法自己升级。

用户的决定（10-14）：
- **主程序做成安装包**（`setup.exe`，用 Inno Setup 打包）。更新就是下载新的安装包、运行它。**不买代码签名证书**（项目不盈利）。
- **插件**：检查服务器或 GitHub，有新版本就下载 jar 替换。
- 更新文件放在两个地方：用户自己的服务器 `https://mcbot.muxueuma.com/` 和 GitHub Releases（放在新开的 GitHub 组织下，免费版）。国内访问 GitHub 有风险，所以先查服务器。
- WebUI 打开时自动检查一次，有新版本只提示，用户点了才更新。
- 下载完只比大小（HTTPS 加上大小一致），不算哈希。
- 版本号用 0.0.1、0.0.2……普通递增；正式 v0.1 发布时跳到 0.1.0。
- 核心模组跟主程序用同一个版本号；每个适配插件有自己的版本号。
- 和启动器的配合保持现在的做法：朋友在 HMCL、PCL 等启动器里自己装 1.21.1 和 NeoForge，WebUI 自动找到游戏目录，插件页往里装模组。不做整合包，使用说明里写清楚步骤。
- **安装包里不带任何模组 jar（核心也不带）**。插件页一律按总清单从服务器或 GitHub 下载我们的 jar，第三方模组照旧从 Modrinth 下载。装模组要联网。
- 要比较版本：游戏里装的版本比清单里的旧，就提示更新（我们的模组以后会更新）。
- 总清单里留一个“公告”类型（纯文字），以后有重构之类的事可以通过它通知。

10-14 先请 Opus 评审过“绿色版原地替换”的方案，结论是在 Windows 上让程序自己替换自己很脆弱：文件被占用、杀毒软件扫描、中途断电都会出问题。改用安装包以后，替换文件、关掉正在运行的程序、重启后再替换这些事都交给 Inno Setup 处理。评审里仍然适用的几条已经写进下面。

## 现在有什么

- 绿色版：`scripts/package.mjs` 打出目录和 zip。双击「启动 mcbot.cmd」，用包里的 `node/node.exe` 运行 `scripts/webui.mjs`。用户自己的数据都在包里的 `runtime/` 和 `memory/`。
- 插件页（`scripts/webui-plugins.mjs`）会把游戏 `mods` 里我们的 jar 和包里的逐字节比较，替换前查游戏是否在运行，替换下来的文件会备份，出错会改回。第三方模组按 `compat.json` 从 Modrinth 下载，并检查大小。
- 已知问题：
  - `package.mjs:129` 打包前会删掉整个目标目录，打到有用户数据的目录会把数据一起删掉。
  - 插件页只认“和包里一样的 jar”，下载地址只放行 Modrinth（`webui-plugins.mjs:18`）。
  - 各处版本号都写死为 0.1.0。

## 一、程序和数据分开

安装包会覆盖安装目录，所以用户数据不能再放在程序旁边。

| | 位置 | 内容 |
| --- | --- | --- |
| 程序目录 | `%LOCALAPPDATA%\Programs\mcbot`（按用户安装，不用管理员权限，不弹 UAC） | Node、运行端、WebUI、托管脚本、`compat.json`、`CLAUDE.md`（不带模组 jar） |
| 数据目录 | `%LOCALAPPDATA%\mcbot` | 原来的 `runtime/`（配置、活动记录、下载缓存、dsh）和 `memory/`（人设、记忆）；卸载时不删 |

- 新加 `scripts/paths.mjs`，统一给出“程序目录”和“数据目录”，各处都从这里取。现在直接拼 `ROOT/runtime`、`ROOT/memory` 的地方都要改：`webui.mjs:25`、`webui-memory.mjs:22`、`webui-games.mjs:303`、`webui-profiles.mjs:235`、`webui-plugins.mjs:228/322`、`start-server-play.mjs:107/113/174`、`agent-models.mjs:106/108`、`driver/args.mjs:59`、`driver/mcp-config.mjs:13`、`agents/dsh-acp.mjs:78`、`agents/process-protocols.mjs:170/175`。
- 数据目录怎么定：有环境变量 `MCBOT_HOME` 就用它；程序目录里有安装标记 `install.json`（只有安装包里有）就用 `%LOCALAPPDATA%\mcbot`；都没有就是开发环境，照旧用仓库里的 `runtime/`、`memory/`。所以仓库里的开发、测试和隔离服脚本都不受影响。
- Agent 的工作目录仍然是程序目录：Claude Code 要从这里读 `CLAUDE.md`，安装目录也不会变。
- WebUI 设置页加“打开数据目录”。
- 你现在那份 0.1.0 绿色版里的 `runtime/`、`memory/`，第一次装安装包时由我手动复制到数据目录。

## 二、版本号

| 部分 | 包含 | 版本 |
| --- | --- | --- |
| 主程序 | 安装包里的全部内容，以及核心模组 `mcbot-server-control`（核心不放进安装包，单独下载，但和主程序同一个版本号） | 一个版本号，例如 0.0.1 |
| 每个适配插件 | 自己的附属 jar（森罗厨房、SB 背包、铁炉、YSM 各一个） | 各自的版本号，写明需要核心不低于哪个版本，以及被适配模组的确切版本 |

- `scripts/set-version.mjs app 0.0.2` 改运行端 `package.json`、核心的 `mod_version`、`compat.json` 里核心的 jar 名。`set-version.mjs <插件 id> 0.0.3` 只改那个插件。`check-compat.mjs` 检查各处是否一致。
- 比较版本时按段比较数字，不按字符串比较。

## 三、安装包

- `scripts/package.mjs` 照旧先摆出程序目录，不再在里面放用户数据，也不再放 `mods/`（jar 由发布脚本单独上传）。打包前如果发现目标目录里有 `runtime/` 或 `memory/`，就拒绝打包，避免误删数据。
- 再用 Inno Setup 打出 `mcbot-setup-0.0.1.exe`：
  - 按用户安装（`PrivilegesRequired=lowest`），在开始菜单和桌面放“mcbot”快捷方式，快捷方式打开 WebUI。
  - 安装时如果 mcbot 还开着，会提示关闭（`CloseApplications`）。
  - 装完可以选择马上打开。静默更新时装完自动重新打开 WebUI。
  - 卸载时问一句“同时删除 mcbot 的数据（人设、记忆、配置、下载缓存）？”，**默认不删**；用户选删除就连数据目录一起删掉（用户 10-14 定：不想在电脑上留垃圾）。提示里写明数据目录的位置，并说明删了无法恢复。静默卸载一律不删数据。
  - 卸载不碰游戏目录：装进游戏 `mods` 的 jar、`config/mcbot-server-control/`、插件页的备份 `mcbot-backups/` 都留在游戏里，因为世界里可能有相关的方块和物品。卸载提示里说明这一点，WebUI 插件页另外提供卸载这些文件的入口。
- 没有代码签名：Windows 会显示“已保护你的电脑”，要点“更多信息 → 仍要运行”。360、火绒这类杀毒软件可能拦截，要选择信任。这些步骤要写进朋友用的说明里。
- Inno Setup 是开发机上的打包工具，需要先下载安装（到时先问用户）。

## 四、总清单 `index.json`

主程序和各插件分开发版，GitHub 的“最新版”地址只能指向一个版本，所以改由我们自己维护一份总清单，WebUI 只读这一份：

```json
{ "schema": 1, "updated": "2026-10-20",
  "sources": ["https://mcbot.muxueuma.com/", "https://github.com/<组织>/<仓库>/releases/download/"],
  "app": { "version": "0.0.2", "date": "2026-10-20", "notes": ["修了……"],
           "file": "app/mcbot-setup-0.0.2.exe", "tag": "app-v0.0.2", "size": 45678901,
           "core": { "file": "core/mcbot-server-control-0.0.2.jar", "size": 345678 } },
  "notices": [
    { "id": "2026-11-01-refactor", "date": "2026-11-01", "title": "下个版本要重新导入人设",
      "text": "……", "level": "info", "appMin": "0.0.1", "appMax": "0.0.9", "until": "2026-12-31" } ],
  "plugins": {
    "kaleidoscope_cookery": { "version": "0.0.3", "date": "2026-10-20", "notes": ["……"],
      "file": "plugins/mcbot-kaleidoscope-cookery-0.0.3.jar", "tag": "kaleidoscope_cookery-v0.0.3", "size": 23456,
      "coreMin": "0.0.2", "...": "其余字段和 compat.json 里这个插件的写法相同（被适配模组的版本、Modrinth 地址、config）" } } }
```

- 服务器和 GitHub 用同一份清单：
  - 服务器地址 = 服务器根地址 + `file`。
  - GitHub 地址 = Release 下载地址 + `tag/` + 文件名。
- `plugins` 由 `release.mjs` 从 `compat.json` 生成，并跑一遍 `check-compat`，不手写，避免和 `compat.json` 对不上（被适配模组的版本会被核心校验）。
- `sources` 记最新的来源地址。WebUI 读到以后存进数据目录，以后改 GitHub 组织名或换地址，旧安装也能找到新地址。服务器地址 `mcbot.muxueuma.com` 要长期不变。
- 核心 jar 和安装包同版本、同一个 Release（`app-v0.0.2`）。清单只写当前版本的核心；装旧版主程序的人要装对应的旧核心时，地址按同样的规则用自己的版本号拼（`core/mcbot-server-control-<版本>.jar`、`app-v<版本>`），所以发过的核心 jar 都要一直保留。
- WebUI 遇到比自己认识的 `schema` 更高的清单就不自动更新，只提示“请到网站下载新版安装包”；遇到不认识的字段直接忽略。

## 五、发布

- `scripts/release.mjs`：打出安装包和各插件 jar，生成新的 `index.json`（没变的部分沿用上一份），在 `output/release/` 里摆成和服务器一样的目录结构。
- 服务器：先上传新文件（传成 `.tmp` 再改名），最后才覆盖 `index.json`。已经发布过的文件名不能再覆盖，因为 zip、jar、exe 会被缓存一年。
- GitHub：用 `gh` 建 `app-v0.0.2` 或 `<插件>-v0.0.3` 的 Release 并上传文件。另有一个固定的 Release `index` 放 `index.json`，每次用 `--clobber` 覆盖。这个 Release 要标成不是最新（`--latest=false`），免得仓库首页的“Latest”指向它。
- 更新说明从交付计划里挑和玩家有关的写，用中文。
- 发布是公开操作，每次上传前都要先问用户。

## 六、主程序更新（WebUI）

- **检查**：WebUI 启动后在后台按顺序读各来源的 `index.json`，每个最多等 5 秒，用第一个读到且格式正确的。读不到也不报错，只在设置页显示“检查更新失败”。有新版本时，页面顶部提示“有新版本 0.0.2”，能展开看更新说明，有一个“更新”按钮。设置页还有手动的“检查更新”。
- **更新**：
  1. 前提：没有正在托管的 Bot，插件页也没有在装卸。判断时不能只看 Bot 的心跳，因为正在等世界开启的托管进程还没有心跳，要像 `game-processes.mjs` 那样查有没有从程序目录启动的 node 进程。
  2. 下载安装包到数据目录的 `updates/`，大小不对就删掉。一个来源下载失败就换下一个。超时按“多久没收到数据”算，不按总时长算。
  3. 用 `/SILENT /SUPPRESSMSGBOXES /NORESTART` 运行安装包（detached），WebUI 随即退出，退出码为 0，页面显示“正在更新，装完自动重新打开”。替换文件、重新打开 WebUI 都由安装包负责。
- **备用的两条路**（Node 下载不走 Clash 这类系统代理，国内网络下可能下不动）：页面上同时给“在浏览器中下载”的链接；用户也可以自己下载安装包直接双击运行，效果一样。
- 回到旧版：重新运行旧版的安装包即可。旧版要能读懂新版写过的数据，所以数据格式只能加字段，不能改含义。

## 七、公告

- `notices` 是纯文字公告，用来通知重构、需要手动处理的事、停服等，不必等发新版本。
- 字段：`id`（唯一，不重复使用）、`date`、`title`、`text`（纯文字，可以换行；WebUI 按文字显示，不解析 HTML 和链接以外的格式）、`level`（`info` 普通、`warn` 重要）、可选的 `appMin`／`appMax`（只给这个版本范围内的主程序看）、可选的 `until`（过了这天不再显示）。
- WebUI 打开时检查到新公告就弹窗；用户点“知道了”后，把 `id` 记进数据目录，不再弹。设置页能看所有公告的历史。
- 发公告只改 `index.json`，同样先问用户再上传。

## 八、插件更新（插件页）

- **所有我们的 jar 都要下载**，安装包里不带。下载按来源顺序到数据目录的 `mod-downloads/`，检查大小，再按现有流程替换（检查游戏是否在运行、备份、出错改回）。下载地址的白名单加上我们自己的来源。没联网、来源都连不上时，插件页说明“需要联网才能安装模组”。
- **比较版本**：读游戏 `mods` 里 jar 的 `neoforge.mods.toml` 拿到已装的版本，按段比较数字，不再和程序目录里的 jar 逐字节比较。
  - **核心**：要装的版本 = 主程序的版本。已装的比它旧 → 显示“有更新”；比它新（例如主程序装回了旧版）→ 显示“核心比主程序新，请更新主程序”；没装 → “安装”。
  - **适配插件**：要装的版本 = 清单里的最新版，前提是主程序满足 `coreMin`。已装的比它旧 → “有更新 0.0.3”，附更新说明；主程序太旧 → “需要先更新主程序到 0.0.x”。被适配模组的版本也变了的话，一起从 Modrinth 换。
  - 没联网读不到清单时，插件页按上一次存下的清单显示，并注明“上次检查于某时”。
- 10-14 实现时发现：定版本号方案之前，我们所有 jar 的版本都写的 0.1.0，按数字比比 0.0.x 新。所以要装的版本低于 0.1.0 时，把游戏里的 0.1.0 当旧版（`webui-plugins.mjs` 的 `LEGACY_VERSION`）。正式发 0.1.0 以后这条自动不起作用；那时还没更新过的旧 jar 会被当成已是最新，所以朋友测试期间要让大家都更新一次。
- 插件页顶部加“全部更新”：核心加上所有已安装的插件，一起出计划，确认后执行。
- 插件页加“从这个游戏移除 mcbot”：移走核心、所有适配 jar 和 `config/mcbot-server-control/`（先备份），被适配的第三方模组保留，因为世界里可能有它们的方块和物品。
- 主程序更新完第一次打开 WebUI 时，如果某个游戏里的模组需要更新，就提示去插件页。
- **启动托管前检查核心版本**：游戏里核心 jar 的版本（读 mods.toml）和主程序不一样时不启动，提示“先关游戏，到插件页更新”。逐字节不同、版本号相同的，只提示不拦。以后在 hello 里带上核心版本，由运行端拒绝不匹配的，这样也能防住“文件换了，但服务器还在跑旧 jar”。

## 九、服务器

- 家里的 Windows 10：nginx 1.28.3 由 nssm 服务 `NginxDerbyHub` 以 SYSTEM 身份运行。SSH 登录发不了 reload 信号，改配置后要 `Restart-Service NginxDerbyHub`（所有走 nginx 的站点会断 1～2 秒，用户 10-14 同意直接重启）。
- 10-14 已经做了：备份 `conf\nginx.conf.before-mcbot-20261014`，新建 `Desktop\mcbot-dist\`，在 nginx 里加了 `mcbot.muxueuma.com` 的静态站点（`index.json` 不缓存，zip、jar 长期缓存），重启服务后其他站点都正常。本机带 Host 头访问能拿到文件。
- **还没通**：从公网访问 `mcbot.muxueuma.com` 仍然打开 DerbyHub，随便一个子域名也一样。说明阿里云 VPS（宝塔）上有一条“所有子域名转给 DerbyHub”的规则。要用户开通 VPS 访问后，给 mcbot 单独加一条保留 Host 的规则，必要时在 frpc 里登记这个域名（frpc 重启时所有隧道会断几秒）。
- 打通以后要用 Node 的 fetch 实测一次，确认 Cloudflare 的机器人防护不会拦下 WebUI 的请求。

## 不做的

- 不做增量更新，每次下载整个安装包（约 40 MB）。
- 不做整合包（用户 10-14 定：保持现在和启动器的配合方式）。
- 不自动更新 Claude Code、Codex、dsh，它们各自更新。
- 不检查哈希，不做代码签名（用户 10-14 定）。

## 估时

- 程序和数据分开：1 天
- 版本号：0.5 天
- 安装包：0.5～1 天
- 总清单和发布脚本：1 天
- 主程序更新：1 天
- 插件更新（全部下载、比较版本、全部更新、移除）：1.5 天
- 公告：0.5 天
- 在干净的 Windows 上装、连升两版、卸载，实测：0.5 天

合计约 6.5～7 天。顺序：程序和数据分开 → 版本号 → 安装包 → 清单和发布 → 主程序更新 → 插件更新 → 公告 → 实测。
