# 陪伴状态设计：姿态、任务、打断

2026-10-10 起草，10-11 四步都做完，10-18 压缩：动工前的现状、逐步的详细设计、估时和各步“和设计的出入”原文在 git 历史里（278f408 版本的本文）。现行规则以[控制协议](server_body_protocol.md#保护姿态和打断)的「保护、姿态和打断」为准，本文只留目标、结论、用户的决定和没做完的事。

**适用范围（2026-10-11 用户定）**：只针对**单人陪伴**，也就是服务器上一个真人玩家和一个 Bot：Bot 陪的就是那个玩家，跟谁就保护谁，听到的命令都当成这个玩家下的。多人的问题记在 [7.9](#79-以后再做多人适配)。

## 1. 为什么改

用户 10-10 觉得托管时的状态管理设计得不好。当时的问题：保护挂在 `follow-companion` 操作底下，等待和做任务时没有保护；跟随让开是“停掉再重建”，到处是新代次还算不算自己的判断；`CompanionMode` 既是模式又是陪挖陪捡的调度器；“忙不忙”的判断散在五处；建筑、种地、长途走被进食或自卫打断就取消；`look-at`、`emote` 这类小动作也走整套让开。同一天的外部评审见[陪伴体验评审](companion_experience_review.md)第 5 条。

## 3. 目标：三层

参照原版生物的 `GoalSelector`（按优先级排的行为，加 MOVE／LOOK 这类互斥标志）：

1. **姿态层（常驻，在服务端）**：跟随、等待、守在某处；**保护谁**是独立的一项，和跟随正交。有任务时姿态在服务端挂起，任务结束后服务端自己恢复，不需要运行端重新提交、也不换代次。
2. **任务层（同时一个）**：统一生命周期 running／suspended／succeeded／failed／cancelled／unknown，每个任务声明能不能续做、此刻能不能被打断。
3. **打断层（按优先级抢占）**：保护玩家 > 近身自卫 > 紧急进食 > 普通进食，统一走“挂起当前任务 → 处理 → 恢复”。

运行端相应改成一个调度器，替代 6 个主人各自的 epoch 和空闲检查；每个工具在注册时声明属性（占不占移动、能否续做、能被谁打断），去掉 `bodyTools` 这类集合和重复的 `assertIdle`。

叫停也分开（与评审第 1 条一致）：暂停当前动作、取消当前任务、紧急停止（清掉所有姿态和保护）是三件事。

## 4. 分步路线

按 1 守卫解耦 → 2 姿态 → 3 小动作 → 4 统一任务生命周期的顺序，每一步单独上线、单独验收；陪挖、陪捡在第 2、4 步里一起拆。

## 5. 第一步：守卫解耦

- 保护绑定一个玩家（名字＋UUID）和选项（范围、撤退血量、弓、盾），战斗逻辑 `GuardCombat` 不改，只改它挂在哪、谁来 tick。
- 生命周期按租约算：普通 `stop` 不清，`stop(clearGuard)`、`revoke`、`release`、新 `claim`、身体变化才清。
- 只在 Bot 离玩家 16 格内接管身体；超出时不覆盖，只有运行端 3 格近身自卫。

### 5.2 哪些时刻可以打断

现行的表在协议[常驻保护](server_body_protocol.md#常驻保护)（`guard-duty-tasks`）。和最初设计的出入：`emote` 手势、`approach-player` 不打断，走向床可打断；期限顺延做成任务的 `resumeAfterGuard(fightMs)`，额度 `GuardDuty.Grace`（最多原期限一倍）；“打架开始前在路上挨打就 `BLOCKED`”没改，打完才重置受伤基线。

### 5.3 运行端：还没做的两项

运行端的保护逻辑留在 `companion-mode.ts`（没有另建 `guard-duty.ts`），`guard` 事件由观察里的 `guard` 生成。设计里有、还没做的：

- `scripts/agents/game-instructions.mjs` 的常驻规则没加“保护是独立开关，跟随、等待、做事时都有效”（`companion-mode` 的工具说明已这样写）。
- WebUI 没有单独显示保护状态（保护谁、是否覆盖、在不在打），只有保护的设置项。

## 6. 用户的决定（2026-10-10）

1. **保护什么时候结束**：明确关掉（`companion-mode guard false`、玩家说不用保护）、**不跟了（`companion-mode stop`）**、紧急停止、撤销控制时结束；任务中途的普通取消不关保护；玩家下线、走远只是暂时不覆盖，回来接着保护。
   - 10-12 评审第 1 条已做（离线）：玩家说“等一下”是暂停，保护不关；说“停”是取消，按 `companion-mode stop` 的说法连保护一起结束；只有急停（WebUI「叫停」、运行端没确认停下）才撤销控制。见 `client-runtime/src/player-stop.ts`。
   - 只在等待（`wait`）中开的保护，`companion-mode stop` 结束等待时也一起关。
2. **离玩家多远还去打**：Bot 离被保护玩家 16 格以内才放下手上的事去打；超出只靠 3 格近身自卫。
3. **打完回哪**：等待中打完回到开始打之前站的地方（在保护范围内）；跟随中打完接着跟；做任务时打完回到任务。

## 7. 第二步：姿态在服务端

用户 10-11 审设计时定的：

1. 删掉 `follow-companion` 操作，用到它的两个实测脚本（`server-body-companion-smoke`、`server-navigation-defense-smoke`）改成 `posture`。
2. 接上前等 3 秒，挪到服务端，常量 `RESUME_AFTER_MS`。
3. 死后、重连后自动恢复姿态（玩家没叫停过），死亡有掉落时先捡回再恢复：掉落还在、走得到、那边没在打怪就去捡，否则直接恢复并告诉模型东西掉在哪、还剩几分钟，不先问玩家。
4. 保护在打时姿态是 `guarding`，打完回到原来的状态；坐着被叫起来不清 `seated`，打完走回座位，座位没了或被占就改成原地等待；等待不记位置，做完事就在做完的地方接着等。
5. 不跑隔离服，打包后用户直接试玩。

### 7.9 以后再做：多人适配

现状：ServerBody 这条路没有“主人”的概念。除了 Bot 自己，所有玩家的聊天都会交给模型（`events.ts` 的聊天事件），由模型决定听不听；跟随要写明玩家名，并用实体 id 确认是同一个人；保护只保护一个玩家。第 2 步不为多人做额外处理，下面这些等做多人时再定：

1. **跟着一个人，保护另一个人**：现在运行端在只开保护时能单独指定要保护的玩家。如果姿态是跟着 A，保护的却是 B，跟随往 A 走，打完架往 B 回，两边会拉扯。第 2 步按单人处理：有跟随时，保护的就是跟随的那个人。
2. **别人让 Bot 做事，做完它会回去找原来的人**：跟着 A 时，B 让它砍树，砍完 3 秒后它会自动接着跟 A，B 可能以为它会留下。做多人时，“接着跟”的事件要写出名字。
3. **别人叫停，也会清掉正在跟的人的姿态**：服务端分不出是谁叫停的。做多人时，要让模型知道发话的不是正在陪的人，或者另加权限。
4. **死后捡装备会捡到别人的东西**：原版的死亡掉落不记是谁掉的。做多人时，服务端给 Bot 死亡时掉出来的物品打标签，只捡带标签的；被别人先捡走的，算正常结束。
5. **陪捡会捡到别人扔的东西**：只按物品种类筛选，是老问题，和第 4 步一起处理。
6. **多个 Bot**：每个 Bot 的姿态和保护各自独立。两个 Bot 跟同一个玩家时，会不会挤在一起、抢同一个怪，都还没看过。

## 8. 第四步：统一任务生命周期

用户 10-11 定 4a～4d 全做、不派 worker，顺序 4b → 4d 服务端 → 4a → 4d 运行端 → 4c，4a 用服务端暂停；只做离线检查，做完打包试玩（不跑隔离服 smoke）；不能暂停时等，血量降到低血线才取消。

### 8.2 4b：工具属性表

`client-runtime/tool-registry.json` 每个 MCP 工具一条：`kind`（read／chat／control／action／task）、`needsIdle`、`moves`、`resumable`、`runsAs`、`clientOnly`。`mcp.ts` 按表注册和查忙，Codex 白名单从表生成，`tool-allowlist.test.mjs` 核对表和实际注册的一致。只看不做的调用（`survey:true`、`dryRun:true`）不重新启用本能、不查忙。

### 8.3 4d 服务端：一个任务槽

9 个任务字段和走路状态收成 `ServerController` 的一个任务槽 `BodyTask`（走路类操作是内部类 `WalkTask`），出错收尾是纯函数 `BodyTask.end`，失败形状由各任务的 `failure()` 返回 `BodyTask.Failure`。手势仍归 `BodyEmotes`。

**待统一**：各任务原有的失败形状不一致（失败结果加不加 `position`、接不接 `RuntimeException`：`PickupItem` 自己收尾，`NativePillar`、`TravelTask` 的异常照旧往上抛）这次照抄没改，代码注释里记着，以后统一。

### 8.4 4a：进食、自卫打断后续做

协议方法 `interrupt`（能力 `task-interrupts`）开“打断窗口”：自动进食、近身自卫、`defend-self` 遇到可续做的任务时暂停它，处理完接着做，期限和保护打架共用一份顺延额度；同一件任务最多续做 2 次（`MAX_RESUMES`）。窗口开着时被暂停的操作和任务从任务槽搬进窗口（`TaskInterrupt`），只放行打断步骤。规则见协议[打断窗口](server_body_protocol.md#打断窗口)。

### 8.5 4d 运行端：一个调度器

`scheduler.ts` 每个身体一份（`Scheduler.of(body)`），容器、采集、生存、垫高四个任务主人的锁、叫停和忙判断都在这里：每个任务是一份租约，开始、能不能走下一步、结束放锁问调度器（`start`／`live`／`end`／`block`）；叫停只有一种 `cancel()`，只有最新一次的确认能收走租约；“停止未确认时不放锁”“结果未知后停住”都落在 `end`。

### 8.6 4c：陪挖、陪捡搬出 CompanionMode

`companion-errands.ts`（`CompanionErrands`）按姿态观察决定什么时候去挖、去捡，陪伴的锁也交给调度器（只占锁、不算正在跑的任务）；`CompanionMode` 只留姿态和保护的翻译。

## 9. 之后的修正

- 10-12：玩家说“等一下”是暂停，保护不关；说“停”是取消，连保护一起结束；只有急停（WebUI「叫停」、运行端没确认停下）才撤销控制（`client-runtime/src/player-stop.ts`）。
- 10-13（ba7dbc6，外部审查）：保护打到一半被关掉或换成新的，和打完走同一套收尾（`DutyFight.end`：被暂停的任务重新寻路、受伤基线从此刻算、期限只给被暂停的操作顺延，没任务时身体站住、姿态接回）；坐着时只有这一拍保护真的会去打才站起来（`GuardDuty.wouldFight` 带上 interruptible）；回座遇到 BUSY／SLEEPING 下一拍再试；打断窗口里被暂停的拾取也收到原版拾取回报。
- 10-13（5bd4bfc）：运行端叫停四处修正，其中死后捡回：`DropWatch` 记下 `explicitStopCount`，之后说过“停”、不带 `keepCompanion` 的 `stop-action` 或 `companion-mode stop`，这次死亡的待捡清单作废；“等一下”不改计数。叫停时读陪伴状态改用没有副作用的 `snapshot()`。
